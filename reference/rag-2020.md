# Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks

来源：https://arxiv.org/abs/2005.11401  
会议：NeurIPS 2020

## 这篇论文真正解决的是什么问题

RAG 解决的不是“模型不会搜索”，而是一个更基础的问题：语言模型把大量知识塞进参数之后，知识更新、可解释性和知识容量都变得昂贵，而且模型回答具体事实时并不能可靠地把参数中的相关知识取出来。

论文把问题拆成两部分：

~~~text
Parametric memory
  模型参数里的语言与世界知识

Non-parametric memory
  模型外部可更新的文档索引
~~~

经典结构可以简化成：

~~~text
question
   ↓
retriever
   ↓
relevant passages
   ↓
generator
   ↓
answer
~~~

当时的实现使用 Wikipedia dense index，说明“模型”和“知识库”可以分开演进。

## 它改变了什么

此前一个容易混淆的假设是：如果模型训练得足够好，它就应该自己记住需要的事实。

RAG 把这个假设拆掉了。知识可以位于模型之外，模型只负责理解问题、利用检索结果和生成答案。

这带来三个直接变化。

### 知识更新和模型更新解耦

外部索引可以重新构建，模型不需要跟着重新训练。对企业系统，这一点比“上下文更长”更重要：制度、产品规则、组织结构和数据定义经常比模型版本变化得快。

### 检索成为模型能力的一部分

RAG 不是简单地把几个文本拼到 prompt 后面。检索质量直接影响生成质量，因此 retrieval 已经成为模型推理链中的前置依赖。

### 知识边界变得显式

模型不必知道所有东西，但系统必须回答：需要知道的时候，从哪里取？

这正是后来的 Agent Knowledge Access、工具调用和上下文工程继续发展的起点。

## 论文证明了什么，没证明什么

原论文在知识密集型问答任务上取得了很强的结果，并展示了外部知识对具体性和事实性的帮助。

但不能从这篇论文直接推出：

- RAG 在所有任务上优于纯模型；
- 一个简单 vector search 就足以支撑企业知识；
- 检索到的文本天然可信；
- RAG 可以替代业务语义层。

原始实验主要研究开放域问答，企业系统还多了权限、freshness、业务术语、结构化数据和审计要求。

## 从 RAG 到今天的 Agent Retrieval

RAG 论文的基本模式是：

~~~text
query → retrieve → generate
~~~

复杂 Agent 往往已经变成：

~~~text
understand query
  ↓
rewrite / decompose
  ↓
retrieve
  ↓
rerank / filter
  ↓
expand context
  ↓
reason
  ↓
verify
  ↓
retrieve again if needed
~~~

变化并不在于“RAG 失效了”，而在于检索从一个固定预处理步骤变成了主动推理的一部分。

## 对 Business Knowledge 的启示

企业 Knowledge Layer 最好从一开始就把“知识”与“检索视图”分开。

~~~text
Canonical Source
      ↓
Knowledge / Semantic Representation
      ↓
Retrieval Index
      ↓
Agent Context
~~~

这样才能允许重新索引、更换 embedding、增加 graph retrieval、增加 metadata filter，并在需要时重新验证。

如果直接把 vector index 当成 Knowledge source，后面一旦索引策略变化，系统很难回答“这条答案当时到底依据了什么”。

## 与当前项目的关系

对 agent-knowledge-usage，RAG 应该被定义成：

> Knowledge Access 的一种实现，而不是 Knowledge 本身。

这一区分决定了后面为什么还需要 Semantic Layer、Graph、Evidence、Memory 和 Context Assembly。
